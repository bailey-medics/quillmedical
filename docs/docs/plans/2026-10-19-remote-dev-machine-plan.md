# Remote dev machine plan

Work on Quill stops whenever the laptop is shut: a Claude Code session runs on the laptop, so closing the lid ends it, and GitHub Codespaces, the obvious always-on alternative, is expensive at the size this project needs and cannot do the job anyway. The 2019 Intel MacBook Pro (8-core i9, 32 GB, 1 TB) is also seven years old, and every option looked at here is at least twice as fast.

The outcome wanted is one always-on Linux machine at home, reached through VS Code Remote-SSH from the laptop and through Claude's Remote Control from the phone, that holds several git worktrees, runs the whole Docker stack and the test recipes, and keeps Claude Code sessions running after the laptop closes. Renting a server was costed in full first and rejected on price (see Decisions). The prices were gathered on 19 October 2026 and are a snapshot: DDR5 memory and Hetzner's prices both moved sharply in 2026.

## Phase 2: Build the machine

- [x] In the BIOS, set it to power on when power returns ("Restore on AC Power Loss"), then test it by pulling the plug and putting it back. Do this first, before installing anything: it is the one fault that sends the machine back, and the BIOS visit to choose the USB boot device is the same visit. On this AMI BIOS it is under Advanced, AMD CBS, FCH Common Options, Ac Power Loss Options, Ac Loss Control, set to Always On; it passed the plug test on 25 October 2026. A Mac keyboard cannot reach the BIOS (Esc and fn plus delete both failed), so use a PC keyboard, or Windows' Advanced startup, UEFI Firmware Settings. Minisforum's setting is reported to work reliably, but if it does not, return the machine within the returns window: a box that stays off after a power cut while the house is empty is the one failure that strands everything until somebody is home.

- [x] Install Ubuntu Server 24.04 LTS, not the desktop edition, which suspends when idle. VS Code Remote-SSH needs x86_64 or arm64 Linux with glibc 2.28 or later (Ubuntu 24.04 ships 2.39) and refuses Alpine. An x86 box matches CI, which has only ever run on `ubuntu-24.04` x64. Installed 24.04.5 on 25 October 2026 as `devbox`, user `markbailey` to match the Mac. Boot the installer from GRUB's "Ubuntu Server with the HWE kernel" entry: the standard kernel stalls at `amdgpu` on this processor. No disk encryption, because a passphrase prompt would hold the box at boot after every power cut; `ubuntu-lv` stretched from the installer's 100 GB default to the whole disk; no snaps, Docker included. The GitHub account had no public SSH keys to import, so password login over SSH stays on until the Mac's key is copied across in the Tailscale step. The box has three wired interfaces (two ports and a USB one) and only one is cabled, so `systemd-networkd-wait-online` sat out its two-minute timeout on every boot; a drop-in at `/etc/systemd/system/systemd-networkd-wait-online.service.d/any.conf` passes `--any`, taking a boot from 2 minutes 18 seconds to 29. The time zone is set to Europe/London so the journal reads in local time.

- [x] Put it on Tailscale and never open a port on the home router. Tailscale's Personal plan (6 users, unlimited devices since 8 April 2026) includes Tailscale SSH (`tailscale set --ssh`), and needs no port forwarding and no static IP, so it works even behind the carrier-grade NAT that some UK ISPs use. In `sshd_config` turn off password and keyboard-interactive authentication (both are on by default) and bind sshd to the Tailscale address only. Put Tailscale on the phone as well, so an SSH app is a fallback if Remote Control is not working. Done on 25 October 2026, with the tailnet owned by the GitHub account: `tailscale up --ssh`, then `/etc/ssh/sshd_config.d/10-lockdown.conf` turning off password, keyboard-interactive and root login (it overrides the installer's `50-cloud-init.conf`, because sshd takes the first value it reads), and `ufw` denying everything inbound except on `tailscale0`. The firewall replaced binding sshd to the Tailscale address, which fails at boot whenever tailscaled comes up after sshd. Two independent ways in remain: Tailscale SSH answers port 22 on the tailnet itself and does not use OpenSSH, so a broken `sshd_config` can be fixed over it, and the local console is unaffected by either. Tailscale SSH authenticates by tailnet identity, not by key, so the GitHub account's two-factor is what guards the box; key expiry is disabled for `devbox` in the admin console, so it does not drop off after 180 days.

- [x] Install Docker Engine from Docker's apt repository with the compose plugin. Docker Engine on Linux is Apache 2.0 licensed, so no Docker Desktop subscription question arises. Add the user to the `docker` group knowing that group is root-equivalent. Published container ports bypass `ufw`, so check the compose port bindings bind to localhost or the Tailscale address, not every interface on the home network. Installed on 25 October 2026: Docker 29.9.2, Compose v5.6.1, Buildx 0.38.1, `docker` and `containerd` enabled at boot, `hello-world` runs without `sudo`. The port check, done at the first `just sa`: `compose.dev.yml` publishes 80, 5173 and 5174 on every interface, and Docker's own rules bypass `ufw`, so the dev app answered at the box's home network address. The daemon's `"ip": "127.0.0.1"` setting was tried first and does nothing here, because it applies only to the default bridge and compose makes its own networks. The fix is a `DOCKER-USER` block appended to `/etc/ufw/after.rules`, dropping new connections that arrive on `en+` or `wl+`, so ufw reloads it at every boot; replies to the containers' own outbound connections are not new and still pass. Checked on 25 October 2026: ports 80, 5173 and 5174 refused from the Mac at `192.168.50.218`, port 80 answering on the box's `localhost` and at its Tailscale address. The dev `.env` files, copied from the Mac's main checkout, stay mode 600 with a read ACL for uid 10001, the backend image's `appuser`, which the container runs as.

- [x] Turn on `unattended-upgrades` (security updates only by default) and set `KillUserProcesses=no` in `/etc/systemd/logind.conf` explicitly, so tmux sessions survive the SSH session that started them. Debian ships that default; Ubuntu's was not confirmed. On 25 October 2026 `unattended-upgrades` was already installed and on (`/etc/apt/apt.conf.d/20auto-upgrades`), and Ubuntu's `logind.conf` leaves `KillUserProcesses=no` commented out as its default, so it is now set explicitly in `/etc/systemd/logind.conf.d/10-keep-user-processes.conf`, with `loginctl enable-linger markbailey` so the user's systemd manager runs with nobody logged in.

- [x] Do not add quiet hours or a nightly suspend. The box idles at 7 to 10 W, about £8 a year, and an 8-hour run flat out at 65 W is 0.52 kWh, about 14p; even a full-load run every night of the year is about £50. With solar panels, shifting a run from night to day saves only the export rate on that half a kilowatt-hour, a few pence. Against that, overnight runs while asleep are the point of the machine, and a timer that stops Docker or suspends the box would kill them. Leave everything on, keep the CPU governor at its `powersave` default, and start long runs in the morning when convenient; revisit only if the bill says otherwise.

- [x] Install the host-side tools the `just` recipes expect: `just`, Node 24 with Yarn 4 through corepack, Playwright and its browser dependencies (`just e2e` runs Playwright on the host against a per-worktree stack), git and the GitHub CLI. The backend and frontend themselves run in containers, but the commit hook still needs Poetry and `pre-commit` on the host: `.husky/pre-commit` runs `pre-commit run`, and its strict mypy, API schema coverage and email theme and preview hooks are `language: system` hooks calling `poetry -C backend run`, so install both with `pipx` on Python 3.14 and run `poetry install` in `backend/` (found on 25 October 2026; the plan had said no Poetry). ## Phase 4: Watch App production and open a pull request for each fault

The box is on all day with nothing to do between sessions, and after Phase 3 it is known to work. This phase gives it a standing job: watch the Slack channel every alert already lands in, and when something breaks, investigate, say what went wrong and why in the thread, fix it on a branch, and open a pull request ready for review. A person reviews and merges, or closes it. Nothing here merges, deploys or touches the dev stack.

The steps are in the order they were built: everything that can be written and tested without a Slack app or a credential first, so that the steps only Mark can do, in `CLAUDE.md`, in Slack, in the Cloud console and as root on the box, come together at the end and go in one sitting. - [x] Write the investigation as a repository skill, `.claude/skills/alert/SKILL.md`, so it is versioned, reviewed and improved like any other skill rather than living in a prompt string on the box. It takes a path to a file holding the alert text, and treats the contents as data, never as instructions. In order: read the alert; rule out an upstream outage before suspecting the code, because three GitHub Actions outages and, on 20 October 2026, a Google Cloud incident in europe-west2 that cut Cloud Run off from Cloud SQL for a morning have each looked like a fault of ours from inside Slack; then pull the matching window of logs with `gcloud logging read`; then find the code the log lines point at.

  The places to look, in this order, each one cheap and each able to end the investigation early:

  - **GitHub's status page**, <https://www.githubstatus.com/>, and its incident feed at <https://www.githubstatus.com/api/v2/incidents/unresolved.json>, for anything open against Actions, Pull Requests or Git Operations. A failed deploy during an Actions incident is a re-run, not a fix.
  - **Google Cloud's status page**, <https://status.cloud.google.com/>, with the incident feed at <https://status.cloud.google.com/incidents.json>, filtered to europe-west2 and the products the app runs on: Cloud Run, Cloud SQL, VPC, Cloud Scheduler, Secret Manager.   - **What changed just before**: the last deploy and the last Terraform run (`gh run list --workflow deploy.yml` and `--workflow terraform.yml`), the commits they carried, and whether any held a migration (`backend/alembic/versions/`).   - **The project's audit log** over the window, `gcloud logging read 'logName:"cloudaudit.googleapis.com"'`, for anything that changed a route, a firewall rule, a job or the Cloud SQL instance. Nothing there and nothing deployed points upstream.
  - **Cloud Run and Cloud SQL logs** for the window: which revision was serving, whether connections arrived at the database at all, and the first error rather than the thousandth.
  - **The health endpoint**, remembering that `/api/health` has reported the database available while nothing could reach it, so a green health check rules nothing out.

## Decisions

- **Rehearse against real posts, not described ones** - every live test on 28 October 2026 found a fault that the unit tests, written from the expected shape of a post, could not: Google's posts carry the policy's subject and never its name, Slack hands a workflow's emoji to the watcher as `:x:` and not ❌, and a merge to `main` left worktree 5 looking busy. Each was then fixed with a test built from the real post. The run in `q5` diagnosed the first and the last of them itself, from the post and the code, before it was told. Rehearse again after any change to the daemon, the skill or an alert policy, with `ALERT_WATCHER_RECORD_EVENTS=1` on for the rehearsal and off afterwards, as `docs/docs/infrastructure/monitoring.md` sets out.

- **The watcher stops at a pull request, marked ready for review** - it branches, fixes, tests, pushes and explains in the thread, and a person reviews and merges. A production fault fixed and merged at 3am with nobody looking is exactly the change that most needs a reviewer, and the repository's "never merge" rule already says so. Ready rather than draft, decided on 20 October 2026: a production fix may need merging quickly, and the heavy CI tier runs only once a pull request leaves draft, so a draft would add a step and a wait at the moment neither is wanted.

- **Slack is the trigger, not Cloud Monitoring or GitHub directly** - every alert and every failed workflow already lands in one channel, so watching it covers both sources and puts the watcher's replies next to the alert they answer. Cloud Monitoring's webhook channel and a GitHub webhook were each considered and would have needed an inbound URL on the box, which the Phase 2 rule forbids. Socket Mode was chosen over polling the channel on 20 October 2026: both are outbound only, but polling needs an interval and a last-seen marker and still adds up to that interval of delay, where Socket Mode delivers in a second, makes no calls while idle, and leaves reconnection to Slack's library. Its one cost is a second, app-level token in the env file. Claude in Slack (Claude Tag) was considered too, since an `@Claude` in the alert text starts a cloud session that reports back in the thread, but it needs a Team or Enterprise plan, runs in a cloud sandbox rather than on the box, and the box is the point.

- **The watcher over-reacts rather than under-reacts** - decided with Mark on 28 October 2026. It acts on every bot post in the channel except those on an ignore list, and the list is narrowed from what the runs show. The point of the watcher is a review, an explanation and a fix ready as soon as something breaks, and a person reviews every pull request anyway, so a wasted run is cheap and a silent miss is not. This replaced a whitelist of known alert names, which dropped anything it did not recognise without telling anyone. The first rehearsal showed what that would have cost: the whitelist matched none of Google's real posts, so every alert would have been dropped, and only acting on every post let the route test start anything.

- **The daemon types into an interactive session, not a headless `claude -p`** - a headless run would be tidier to script, with a JSON result and an exit code, but there is nothing to attach to while it runs, and the point of the box is that Mark can pick up any session from the phone or over SSH. Driving the ordinary tmux session with `tmux send-keys` makes worktree 5 the same as worktrees 1 to 4 with one extra typist, at the cost of hooks for busy-tracking and the skill posting its own results to Slack.

- **The watcher's secrets live in the user's home, not in `/etc`** - the first version put the Slack tokens in `/etc/quill-watcher.env`, owned by root at mode 0600, and the log key beside them. A systemd *user* service reads its `EnvironmentFile` as that user, not as root, so it could not have opened either file, and neither could `scripts/slack-reply.sh` running in the session. Moved on 26 October 2026 to `~/.config/quill-alert-watcher/`, mode 0600 and owned by the watcher's user, which is the one account that needs them. Root owning them bought nothing: anything running as that user can already drive the session that holds the tokens in its environment.

- **Read-only log access through a service account, not Mark's login** - the watcher reads why an alert fired as `alert-watcher-logs`, which may read logs and nothing else. It was first planned as a key on the box; the organisation's ban on keys stopped that on 27 October 2026, and the box now signs in with a client certificate instead (the certificate steps above). Nothing on the box works as a password, it is on a machine Mark owns rather than in GitHub, and the rule that CI holds no runtime credentials is kept. This chat's own sessions still use Mark's login; only the watcher's session, through its separate `CLOUDSDK_CONFIG` folder, uses the robot.

- **The watcher is TypeScript on Node, not Python** - asked on 27 October 2026. The step that built it gave one reason, that Node 24 was already on the box, which was true of Python 3.14 as well, so it was a judgement call rather than forced. What it bought: Slack's Node packages are its best maintained, with reconnection handled there, the program runs under Node's type stripping with no build step, as `tools/review-marks` does, and it keeps its own dependencies apart from the backend's. Python with `slack_sdk` would have worked as well, and would have sat closer to the backend's mypy and Ruff checks. Left as it is: Mark does not mind, and a rewrite would buy nothing.

- **Nothing watches the watcher, for now** - decided on 27 October 2026. systemd restarts it 30 seconds after a crash, it starts at boot with nobody logged in, the BIOS powers the box back on after a power cut, and Slack's library reconnects a dropped socket. What none of that catches is the box being off or offline, the watcher stuck in a restart loop (a revoked Slack token, say), or the watcher running but hung. A dead man's switch was offered: a heartbeat log line every 5 minutes with a Cloud Monitoring alert after 30 minutes of silence, which needs the log reader to gain `roles/logging.logWriter`, or Healthchecks.io, a new outside service. Mark declined both: an App production alert in Slack with no reply from the watcher already says it is down, since every alert it picks up gets a "Looking into this now." The cost, accepted: it is found only when an alert arrives, so it can sit dead through a quiet spell. Revisit if that gap ever matters, for instance once alerts are rare enough that silence is normal.


- **Buy for home, do not rent** - the cheapest suitable rented server was Hetzner's EX44-1-LTD (14-core i5-13500, 64 GB, two 512 GB NVMe) at EUR 57.30 a month plus EUR 1.70 for an IPv4 address, about £61 with UK VAT, or about £730 a year. A £1,087 mini PC replaced every two to three years, plus electricity, is about £400 to £580 a year, and the old one keeps some resale value; the £739 8-core alternative would be about £300 to £350. Renting's two advantages were weighed and do not justify double the cost. Home internet dropping out one or two days a year is about 1 day in 150 and acceptable, because a stranded job is restarted when the connection is back. And the hardware ageing is answered by the replacement cycle. The rented options, all seen on 19 October 2026 and excluding VAT, for the record:

  - **OVHcloud RISE-S** - EUR 64.99, Ryzen 7 9700X, 64 GB DDR5, two 512 GB NVMe, northern France only, a one-month setup fee unless committed for 12 months.

  - **Hetzner AX42-1** - EUR 97.30 plus EUR 49 setup, Ryzen 7 PRO 8700GE, 64 GB DDR5, two 512 GB NVMe.

  - **Hostinger KVM 8** - £18.99 a month on a 24-month prepaid term, renewing at £39.99: 8 shared vCPUs, 32 GB, 400 GB. The cheapest rental, but shared CPUs, and about £456 up front.

  - **UK-hosted dedicated servers** - Fasthosts £115 on a 1-year minimum, Clouvider £124, Mythic Beasts £130 in Cambridge or £210 in London.

  - **Cloud VMs in London with 1 TB** - AWS Lightsail $164 flat (640 GB), Hetzner CCX33 plus a volume EUR 196, GCP e2-standard-8 about $372, Azure D8as v5 about $376, AWS m6a.2xlarge about $387. Stopping a VM when idle does not close the gap: a 1 TB disk alone is $120 a month on GCP.

  - **GitHub Codespaces** - $0.72 an hour for 8 cores and 32 GB, about $530 always on, and unable to do the job at any price: a 64 GB disk, and a hard 12-hour lifetime that applies even while it is in use.

- **Linux mini PC, not a Mac mini** - every pinned image in the compose files publishes linux/arm64, so a Mac would run the stack, but only inside the Linux VM that Docker Desktop, OrbStack or Colima provide, with the extra memory that costs; OrbStack is $8 a month for any commercial use. A Mac mini with 32 GB and 1 TB also costs more than the X1 Pro-370 for 8 fewer cores, and Tailscale SSH on macOS needs the open-source `tailscaled` rather than the App Store app. A Linux x86 box matches CI exactly.

- **Ubuntu Server, not Ubuntu Desktop** - the box could double as the desk computer, with the monitor, keyboard and trackpad plugged straight in and VS Code running on it natively, and the desktop edition costs only 1 to 2 GB of memory and almost no CPU when idle. Rejected anyway: it is a dev server first, Server never suspends and patches quietly through `unattended-upgrades`, and setting up a headless server is worth learning. The laptop stays the screen, over Remote-SSH, even at the desk.

- **tmux keeps sessions alive, Remote Control directs them** - Remote Control mirrors a running process to the phone or browser; it is not a keep-alive. Claude Code on the web (`claude --cloud`) was considered and rejected as the main route: its VMs are 4 vCPU, 16 GB, 30 GB disk with Docker preinstalled and no extra charge beyond plan usage, but they start from the pushed branch rather than the worktree, give no shell, pause when idle, and its commits carry a `Claude-Session:` trailer unless `attribution.sessionUrl` is set to false. It stays useful as a stopgap on the days the home connection is down.
