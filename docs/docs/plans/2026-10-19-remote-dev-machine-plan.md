# Remote dev machine plan

Work on Quill stops whenever the laptop is shut: a Claude Code session runs on the laptop, so closing the lid ends it, and GitHub Codespaces, the obvious always-on alternative, is expensive at the size this project needs and cannot do the job anyway. The 2019 Intel MacBook Pro (8-core i9, 32 GB, 1 TB) is also seven years old, and every option looked at here is at least twice as fast.

The outcome wanted is one always-on Linux machine at home, reached through VS Code Remote-SSH from the laptop and through Claude's Remote Control from the phone, that holds several git worktrees, runs the whole Docker stack and the test recipes, and keeps Claude Code sessions running after the laptop closes. Renting a server was costed in full first and rejected on price (see Decisions). The prices were gathered on 19 October 2026 and are a snapshot: DDR5 memory and Hetzner's prices both moved sharply in 2026.

AMD Ryzen AI 9 HX 370 (12 cores, 24 threads, Zen 5): about 1.8 times the 2019 MacBook's speed on one core and well over twice across all cores (Geekbench 6 roughly 2,800 and 14,500 against 1,500 and 6,800), without the i9's throttling; two DDR5 SO-DIMM slots up to 128 GB, three M.2 slots, a built-in power supply, 65 W maximum and 45 dB at full load. Buy from a UK seller with easy returns, because Minisforum has more early-failure reports (power board capacitors, internal power supply) than Beelink, offset by a two-year warranty and well-regarded repairs. ## Phase 2: Build the machine

- [x] In the BIOS, set it to power on when power returns ("Restore on AC Power Loss"), then test it by pulling the plug and putting it back. Do this first, before installing anything: it is the one fault that sends the machine back, and the BIOS visit to choose the USB boot device is the same visit. On this AMI BIOS it is under Advanced, AMD CBS, FCH Common Options, Ac Power Loss Options, Ac Loss Control, set to Always On; it passed the plug test on 25 October 2026. A Mac keyboard cannot reach the BIOS (Esc and fn plus delete both failed), so use a PC keyboard, or Windows' Advanced startup, UEFI Firmware Settings. Minisforum's setting is reported to work reliably, but if it does not, return the machine within the returns window: a box that stays off after a power cut while the house is empty is the one failure that strands everything until somebody is home.

- [x] Install Ubuntu Server 24.04 LTS, not the desktop edition, which suspends when idle. VS Code Remote-SSH needs x86_64 or arm64 Linux with glibc 2.28 or later (Ubuntu 24.04 ships 2.39) and refuses Alpine. An x86 box matches CI, which has only ever run on `ubuntu-24.04` x64. Installed 24.04.5 on 25 October 2026 as `devbox`, user `markbailey` to match the Mac. Boot the installer from GRUB's "Ubuntu Server with the HWE kernel" entry: the standard kernel stalls at `amdgpu` on this processor. No disk encryption, because a passphrase prompt would hold the box at boot after every power cut; `ubuntu-lv` stretched from the installer's 100 GB default to the whole disk; no snaps, Docker included. The GitHub account had no public SSH keys to import, so password login over SSH stays on until the Mac's key is copied across in the Tailscale step. The box has three wired interfaces (two ports and a USB one) and only one is cabled, so `systemd-networkd-wait-online` sat out its two-minute timeout on every boot; a drop-in at `/etc/systemd/system/systemd-networkd-wait-online.service.d/any.conf` passes `--any`, taking a boot from 2 minutes 18 seconds to 29. The time zone is set to Europe/London so the journal reads in local time.

- [x] Put it on Tailscale and never open a port on the home router. Tailscale's Personal plan (6 users, unlimited devices since 8 April 2026) includes Tailscale SSH (`tailscale set --ssh`), and needs no port forwarding and no static IP, so it works even behind the carrier-grade NAT that some UK ISPs use. In `sshd_config` turn off password and keyboard-interactive authentication (both are on by default) and bind sshd to the Tailscale address only. Put Tailscale on the phone as well, so an SSH app is a fallback if Remote Control is not working. Done on 25 October 2026, with the tailnet owned by the GitHub account: `tailscale up --ssh`, then `/etc/ssh/sshd_config.d/10-lockdown.conf` turning off password, keyboard-interactive and root login (it overrides the installer's `50-cloud-init.conf`, because sshd takes the first value it reads), and `ufw` denying everything inbound except on `tailscale0`. The firewall replaced binding sshd to the Tailscale address, which fails at boot whenever tailscaled comes up after sshd. Two independent ways in remain: Tailscale SSH answers port 22 on the tailnet itself and does not use OpenSSH, so a broken `sshd_config` can be fixed over it, and the local console is unaffected by either. Tailscale SSH authenticates by tailnet identity, not by key, so the GitHub account's two-factor is what guards the box; key expiry is disabled for `devbox` in the admin console, so it does not drop off after 180 days.

- [x] Install Docker Engine from Docker's apt repository with the compose plugin. Docker Engine on Linux is Apache 2.0 licensed, so no Docker Desktop subscription question arises. Add the user to the `docker` group knowing that group is root-equivalent. Published container ports bypass `ufw`, so check the compose port bindings bind to localhost or the Tailscale address, not every interface on the home network. Installed on 25 October 2026: Docker 29.9.2, Compose v5.6.1, Buildx 0.38.1, `docker` and `containerd` enabled at boot, `hello-world` runs without `sudo`. The port check, done at the first `just sa`: `compose.dev.yml` publishes 80, 5173 and 5174 on every interface, and Docker's own rules bypass `ufw`, so the dev app answered at the box's home network address. The daemon's `"ip": "127.0.0.1"` setting was tried first and does nothing here, because it applies only to the default bridge and compose makes its own networks. The fix is a `DOCKER-USER` block appended to `/etc/ufw/after.rules`, dropping new connections that arrive on `en+` or `wl+`, so ufw reloads it at every boot; replies to the containers' own outbound connections are not new and still pass. Checked on 25 October 2026: ports 80, 5173 and 5174 refused from the Mac at `192.168.50.218`, port 80 answering on the box's `localhost` and at its Tailscale address. The dev `.env` files, copied from the Mac's main checkout, stay mode 600 with a read ACL for uid 10001, the backend image's `appuser`, which the container runs as.

- [x] Turn on `unattended-upgrades` (security updates only by default) and set `KillUserProcesses=no` in `/etc/systemd/logind.conf` explicitly, so tmux sessions survive the SSH session that started them. Debian ships that default; Ubuntu's was not confirmed. On 25 October 2026 `unattended-upgrades` was already installed and on (`/etc/apt/apt.conf.d/20auto-upgrades`), and Ubuntu's `logind.conf` leaves `KillUserProcesses=no` commented out as its default, so it is now set explicitly in `/etc/systemd/logind.conf.d/10-keep-user-processes.conf`, with `loginctl enable-linger markbailey` so the user's systemd manager runs with nobody logged in.

- [x] Do not add quiet hours or a nightly suspend. The box idles at 7 to 10 W, about £8 a year, and an 8-hour run flat out at 65 W is 0.52 kWh, about 14p; even a full-load run every night of the year is about £50. With solar panels, shifting a run from night to day saves only the export rate on that half a kilowatt-hour, a few pence. Against that, overnight runs while asleep are the point of the machine, and a timer that stops Docker or suspends the box would kill them. Leave everything on, keep the CPU governor at its `powersave` default, and start long runs in the morning when convenient; revisit only if the bill says otherwise.

- [x] Install the host-side tools the `just` recipes expect: `just`, Node 24 with Yarn 4 through corepack, Playwright and its browser dependencies (`just e2e` runs Playwright on the host against a per-worktree stack), git and the GitHub CLI. The backend and frontend themselves run in containers, but the commit hook still needs Poetry and `pre-commit` on the host: `.husky/pre-commit` runs `pre-commit run`, and its strict mypy, API schema coverage and email theme and preview hooks are `language: system` hooks calling `poetry -C backend run`, so install both with `pipx` on Python 3.14 and run `poetry install` in `backend/` (found on 25 October 2026; the plan had said no Poetry). The stack recipes (`just stack-new`, `just stu`, and so `/crpd`) run `scripts/check-python-version.sh host` and refuse a `python3` older than the one in `.python-version` (3.14.7 today), Ubuntu 24.04 ships 3.12, so install `python3.14` from the deadsnakes PPA and put a symlink to it at `~/.local/bin/python3`, first on the user's PATH. Never repoint the system `python3` with `update-alternatives`: apt and its tooling run on it and break. The guard compares minor versions only, so patch releases do not matter. `gh` falls back to a plain-text token file on a headless box, so prefer an SSH key for git and give `gh` a fine-grained token with the minimum scopes. Done on 25 October 2026: Python 3.14.9 from deadsnakes behind `~/.local/bin/python3`, Node 24.22.1 from NodeSource with corepack (Yarn 4.18.1 inside the repository), `just` 1.59.0 from just.systems, Poetry 2.5.1 and pre-commit 4.7.0 through `pipx`, `gh` 2.103.2 from GitHub's apt repository, tmux, and Playwright's Chromium and WebKit with their system libraries. `gh` signed in through the browser device flow rather than a fine-grained token, because the stack recipes and `/crpd` use it for pull requests, checks and the merge queue and a fine-grained token's permissions for all of that are fiddly to get right; it generated a passphrase-free ed25519 key, uploaded to GitHub as `devbox`, since a passphrase would stall unattended pushes from tmux, and its token sits in `~/.config/gh/hosts.yml`, readable by the user only.

- [x] Recreate the worktree layout as on the laptop, plus one: the main checkout (`quillmedical`) and its numbered worktrees side by side under `~/github/`, `quillmedical-2` to `quillmedical-4` as on the laptop and a fifth, `quillmedical-5`, kept for the Slack alert watcher in Phase 4, which runs there and nowhere else, then `just initialise-repo` for the hooks. The recipes already keep worktrees apart, and nothing changes on Linux: `just ub` and `just uf` run a throwaway container per worktree (compose project `quill-test-<dir>`), `just e2e` brings up `quill-e2e-<dir>` on a free port, `just migrate` uses `quill-migrate-<dir>`, and `just sa` refuses outside the main checkout. The `local/` folder is per machine and gitignored, so copy over by hand only what the box needs, into the main checkout only. Done on 25 October 2026 with `git worktree add --detach ../quillmedical-$n origin/main` for 2 to 5, `just initialise-repo` in the main checkout, `yarn install` in each worktree's `frontend/` and `poetry install` in every `backend/`, not `just pi`, which also runs `poetry lock` and could rewrite the lock file in a fresh checkout. Nothing from `local/` was needed yet.

## Phase 3: Connect the laptop and the phone

- [x] Connect VS Code Remote-SSH to the box's Tailscale hostname, one window per worktree. VS Code Server installs under the user on the remote, workspace extensions run there, and the Claude Code extension sets no `extensionKind`, so it runs on the box with its bundled `claude` binary. Install the standalone `claude` CLI on the box as well for the integrated terminal. Headless login is the documented copy-URL, paste-code flow for SSH sessions; credentials land in `~/.claude/.credentials.json` with mode 0600. Done on 25 October 2026: Remote-SSH to `devbox`, the Claude Code extension 2.1.310 installed into the remote with "Install in SSH: devbox" (a Mac extension does not carry over), the standalone CLI from `claude.ai/install.sh` at the same version, and one sign-in that the extension and the CLI share.

Anthropic's own docs say to start `claude` inside tmux or screen on a remote machine; a VS Code terminal and the extension's panel both die when the window disconnects. - [x] Run `/rc` (Remote Control) inside each tmux session to direct it from the phone or claude.ai when out. It is a window onto the running process, not a keep-alive, which is why tmux comes first; it needs outbound HTTPS only, survives network drops, works on Pro and Max but not on API keys, and needs the directory trusted interactively once before it can be used. Confirmed on 25 October 2026: `q1` answered from the Claude app on the iPhone with VS Code closed. The phone needs only the Claude app, not Tailscale, because Remote Control runs through Anthropic's servers.

- [x] Run one full cycle from the main checkout and from a worktree before relying on it: `just sa`, `just ub -k "..."`, `just uf src/...`, `just e2e`, `just sbt`, and a `just migrate` dry run. Progress on 25 October 2026: `just ub -k health` (4 passed) and `just uf src/securityTxt.test.ts` (3 passed) from `quillmedical-2`, and `just sa` up healthy with its migrations applied; `just e2e`, `just sbt` and a `just migrate` dry run still to do. `just sa` and `just se` print `Access the frontend at: http://` with `ipconfig: command not found` on Linux, because they read the address with macOS's `ipconfig getifaddr en0`; harmless, but a code fix for the same `implement` as the Vite change below. Then, from `quillmedical-2`: `just e2e` passed, 374 tests in 2.9 minutes against 13.3 minutes for the same 374 in CI's E2E job on 23 October 2026. The 2019 MacBook, run the same evening for comparison, took 5.9 minutes for the tests and 7 minutes 11 seconds overall, and 3 of the 374 failed on timeouts that pass on the box and in CI. `just sbt` and `just migrate` both failed on file ownership, which the next step fixes. With that fix, from `quillmedical-3`: the full `just ub`, 7,641 passed, 3 skipped and 2 expected failures, as the host user and leaving nothing owned by anyone else; `just sbt`, 929 passed and 3 skipped; and the `just migrate` dry run wrote its revision, found it empty and removed it, as it should.

- [x] Make the containers write into a worktree as the host user, a code change needing `implement`. Docker Desktop on the Mac maps file ownership across a bind mount, so nobody noticed that containers here write as whatever user their image runs as; a Linux host keeps the real numbers. Two failures followed on 25 October 2026. The frontend unit-test container runs as root, so `frontend/src/generated/*.json` came out owned by root and the next host-side `just sbt` stopped at `EACCES` regenerating `base-professions.json`. And `compose.migrate.yml`'s container runs as the backend image's `appuser`, uid 10001, which cannot write into a worktree owned by uid 1000, so `just migrate` stopped at `PermissionError` writing its revision (nothing was left behind). The Justfile now exports `HOST_UID` and `HOST_GID` on Linux only, empty on a Mac so nothing changes there. The backend unit-test and migrate services run as `"${HOST_UID:-10001}:${HOST_GID:-10001}"`, which also ends the `.pytest_cache` warning. The frontend service stays root, because its `node_modules` named volumes are root's and vitest writes its cache there, and instead runs every command through `scripts/hand-back-ownership.sh`, which chowns what the run wrote outside `node_modules` back to the host user and keeps the command's exit status; `scripts/tests/hand-back-ownership.bats` covers it with a stub `chown`, so it needs no root. `compose.ci.yml` is left alone: the E2E backend writes `frontend/e2e/.mail/` and `.e2e-teaching/` as uid 10001 into folders the prepare scripts open to everyone and empty on the next run, which CI depends on and which did not get in the way here. Rootless Docker on the box was considered and rejected: it maps the containers' root to the host user, but uid 10001 would still land on an unwritable subordinate uid, so `just migrate` would still fail.

- [x] Open the dev app in a browser two ways and fix what the second one shows. First through VS Code's port forwarding, which makes `localhost` on the laptop reach the box, so everything behaves as it does today. Then by the box's Tailscale address from the phone. The frontend calls `/api` relatively through Caddy (`caddy/dev/Caddyfile`), so nothing in the browser path hard-codes `localhost`, but two things will: Vite blocks any `Host` header that is not `localhost` or an IP address, and `frontend/vite.config.ts` sets no `server.allowedHosts`, so `http://devbox` gets a 403 from Vite while `http://100.x.y.z` works; and `FRONTEND_URL` in `backend/app/config.py` defaults to `http://localhost`, which is only used to build the links in verification and reset emails. The fixes are `allowedHosts` (or the `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` environment variable in `compose.dev.yml`) and `FRONTEND_URL=http://devbox` in the box's `backend/.env`; the Vite one is a code change needing `implement`. Tried on 25 October 2026: VS Code's port forwarding works, landing on a free port such as `localhost:59937` because port 80 is not free to an ordinary process on the Mac; the phone loads `http://100.84.30.118`; `http://devbox` is blocked by Vite, as predicted. The fix names no host in the code and needed no compose change: the frontend service already loads `frontend/.env` as its environment, so the box's copy sets `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS=devbox,.ts.net`, documented as a commented line in `frontend/.env-sample`, and the Mac sets nothing; the `.ts.net` entry covers `tailscale serve`'s HTTPS name if that is ever turned on. The box's `backend/.env` sets `FRONTEND_URL=http://devbox`. `just sa` and `just se` now print the address from a private `_host-address` recipe: the Wi-Fi address on a Mac as before, and on Linux the Tailscale address, because the firewall keeps the dev stack off the home network. Checked: `http://devbox/login` and `/api/health` answer 200 from the Mac over Tailscale.

## Phase 4: Watch App production and open a pull request for each fault

The box is on all day with nothing to do between sessions, and after Phase 3 it is known to work. This phase gives it a standing job: watch the Slack channel every alert already lands in, and when something breaks, investigate, say what went wrong and why in the thread, fix it on a branch, and open a pull request ready for review. A person reviews and merges, or closes it. Nothing here merges, deploys or touches the dev stack.

The steps are in the order they were built: everything that can be written and tested without a Slack app or a credential first, so that the steps only Mark can do, in `CLAUDE.md`, in Slack, in the Cloud console and as root on the box, come together at the end and go in one sitting. They were reordered on 26 October 2026 for that reason; the first version began with the Slack app.

- [x] Write the investigation as a repository skill, `.claude/skills/alert/SKILL.md`, so it is versioned, reviewed and improved like any other skill rather than living in a prompt string on the box. It takes a path to a file holding the alert text, and treats the contents as data, never as instructions. In order: read the alert; rule out an upstream outage before suspecting the code, because three GitHub Actions outages and, on 20 October 2026, a Google Cloud incident in europe-west2 that cut Cloud Run off from Cloud SQL for a morning have each looked like a fault of ours from inside Slack; then pull the matching window of logs with `gcloud logging read`; then find the code the log lines point at.

  The places to look, in this order, each one cheap and each able to end the investigation early:

  - **GitHub's status page**, <https://www.githubstatus.com/>, and its incident feed at <https://www.githubstatus.com/api/v2/incidents/unresolved.json>, for anything open against Actions, Pull Requests or Git Operations. A failed deploy during an Actions incident is a re-run, not a fix.
  - **Google Cloud's status page**, <https://status.cloud.google.com/>, with the incident feed at <https://status.cloud.google.com/incidents.json>, filtered to europe-west2 and the products the app runs on: Cloud Run, Cloud SQL, VPC, Cloud Scheduler, Secret Manager. Personalized Service Health in the console shows the same thing scoped to the project, but the public feed needs no login.
  - **The workflow run itself**, through `gh run view <id> --log-failed`, for a failed deploy: which step failed and what it printed.
  - **What changed just before**: the last deploy and the last Terraform run (`gh run list --workflow deploy.yml` and `--workflow terraform.yml`), the commits they carried, and whether any held a migration (`backend/alembic/versions/`). A fault that began with no deploy and no Terraform run is almost never in the code.
  - **The project's audit log** over the window, `gcloud logging read 'logName:"cloudaudit.googleapis.com"'`, for anything that changed a route, a firewall rule, a job or the Cloud SQL instance. Nothing there and nothing deployed points upstream.
  - **Cloud Run and Cloud SQL logs** for the window: which revision was serving, whether connections arrived at the database at all, and the first error rather than the thousandth.
  - **The health endpoint**, remembering that `/api/health` has reported the database available while nothing could reach it, so a green health check rules nothing out.

  When the cause is upstream, the skill says so in the thread with the incident link, opens no pull request, and lists what to do when the incident closes: re-run the deploy, confirm an admin job execution succeeds, force-run any scheduled job that missed its slot. The daemon treats the incident as the fingerprint, so the hourly alerts that follow do not each start a run. Otherwise, it writes a failing test that reproduces the fault, so the pull request proves the diagnosis; fixes it; runs the targeted tests with `just ub -k` or `just uf <file>`; posts the root cause to the thread through `scripts/slack-reply.sh` as soon as it is known, before the fix; then `just stack-new` and `/crpd ready`, so the pull request opens ready for review rather than as a draft, because a production fix may need merging at once; and finishes by posting a short summary of root cause, fix and pull request link to the thread, again through `scripts/slack-reply.sh`. If it cannot reproduce the fault, it says so with what it checked and opens no pull request. It takes the thread to reply to from the alert file, which the daemon writes there. The skill never runs `/f`, never merges, and never touches `infra/`, `.github/workflows/`, migrations or `CLAUDE.md`: a change in any of those is reported in the thread as a suggestion for a person to make.

  Two things were added while writing it. The skill commits and pushes only when `QUILL_ALERT_WATCHER=true`; run by hand on a pasted alert, in any worktree, it stops before `just stack-new` and reports, because the standing permission in `CLAUDE.md` is the watcher's and nobody else's. And its `allowed-tools` frontmatter names the read-only commands it needs, `gcloud logging read`, `gh run view`, `gh run list` and `scripts/slack-reply.sh`, so the permission is versioned with the skill rather than living only in the systemd unit's `--allowedTools`; the unit keeps its list too, for the commands `/crpd` runs.

- [x] Give the skill its voice and the daemon its busy flag, as two small shell scripts with bats tests beside the others. `scripts/slack-reply.sh <alert-file> <message|->` posts one message into the alert's thread with `chat.postMessage`. It reads the channel and thread from the alert file's header and nowhere else, checks both against Slack's formats before using them, and reads `SLACK_BOT_TOKEN` from the environment or, failing that, from the env file of the last step, without sourcing it. The token goes to curl on a header file rather than on the command line, so it never shows in `ps`, and a message is cut at 3,900 characters, under Slack's 4,000, with a note that it was. `SLACK_REPLY_DRY_RUN=1` prints the request instead of sending it, which is what the tests use. `.claude/hooks/alert-watcher-busy.sh set|clear`, wired in `.claude/settings.json` as a `UserPromptSubmit` and a `Stop` hook, writes and removes a flag file holding the time the turn began, under `~/.local/state/quill-alert-watcher/`. It does nothing at all unless `QUILL_ALERT_WATCHER=true`, so worktrees 1 to 4 and every other machine never see it, and it always exits 0, because a `UserPromptSubmit` hook that exits 2 blocks the prompt.

- [x] Write the daemon as a small Node and TypeScript program in `scripts/alert-watcher/`, with its own `package.json` under Yarn 4, using Slack's `@slack/socket-mode` and `@slack/web-api` packages, pinned. Node 24 is already on the host from Phase 2, so this adds no runtime. Add the directory to `.github/dependabot.yml` so its two dependencies are watched like everything else. The daemon does four things and no more: it subscribes to the channel over the socket and matches only two shapes of message, a Cloud Monitoring alert post and a `*❌ Deploy failed*` post from `deploy.yml`, ignoring `*✅ Deployed*` and everything a person writes; it fingerprints each (policy name and the date, or workflow and commit) and runs each fingerprint once, with a cap of six runs a day so a flapping alert cannot burn the plan; it posts "Picked this up in worktree 5" in the thread, with a link to the thread written into the alert file so the skill can reply there; and it drives the session, writing the alert text to a file in the watcher's state folder and sending `/clear` then `/alert <file>` to the tmux pane with `tmux send-keys`. It never calls `claude -p`: a headless run has nothing to attach to. It knows whether the session is busy from the flag file the hooks above keep, and it queues alerts while the flag is set, whether the session is busy with an alert or with Mark. Permission prompts would stall a run with nobody to answer them, so the session in worktree 5 is started with an allowlist naming only what the skill needs beyond reading and testing: `just stack-fresh`, `just stack-new`, `just stack-submit`, `just stu`, `git push`, `gh pr create`, `gh pr edit`, `gh pr ready`, `gcloud logging read` and `scripts/slack-reply.sh`. Anything outside it is refused, and the skill reports that in the thread rather than waiting. The thread gets its root cause and its final summary from the skill itself through `scripts/slack-reply.sh`, not from the daemon, which has no result to read; a run that is killed or stalls past 45 minutes is noticed by the `Stop` hook not firing, and the daemon then posts that and sends Escape.

  Worktree 5 is a worktree to work in as well as the watcher's, so a person may be in it, and the daemon never resets or cleans it. Before a run it checks that the tree is clean and on `origin/main` or a `feature/alert-*` branch, and if it is not, it replies in the thread that worktree 5 is in use and parks the alert until the tree is clean again. Leaving work uncommitted there is therefore what stops the watcher, which is the right way round. This was a step of its own, "Add a fifth worktree", until the reorder: the worktree itself was made in Phase 2, so what was left of the step was this check, and the tmux session the systemd unit starts.

  What building it settled, on 26 October 2026:

  - **The alert policies are a whitelist** in `scripts/alert-watcher/src/messages.ts`, one entry per policy in `infra/modules/monitoring/main.tf`, and a test reads `main.tf` and fails when a policy there is missing from the list. A pattern on the ` (app)` suffix was the alternative and would have picked up a new policy without anyone looking at whether it is a fault to fix; the whitelist makes that a decision. The four-weekly alert route test and the retention decision are on the ignore list from the start, rather than waiting for the rehearsal to show they start a run, because both are known not to be faults.
  - **Google Cloud doesn't document the exact shape of its Slack posts.** No published description of the native Slack channel's message fields was found, so the matcher reads every `text`, `title`, `pretext`, `fallback` and `value` string in the message, its attachments and its blocks, and finds the policy name in that. `ALERT_WATCHER_RECORD_EVENTS=1` saves the raw events to the state folder, so the rehearsal can check the shapes, and the closing words in particular, against real posts. A bot message it does not recognise is logged as `unmatched`, without its text.
  - **A Google Cloud incident post starts a run of its own**, so the skill posts the list of what to do when the incident closes; every other alert in the next twelve hours, or until a post with `State: RESOLVED`, gets a one-line reply pointing at the incident's thread and no run.
  - **A person's turn is never interrupted.** Only a run the daemon started is stopped at 45 minutes. A busy flag with no run behind it is cleared only once it is three hours old, which is what an Escape before the `Stop` hook leaves behind.
  - **The alert files go in the state folder**, `~/.local/state/quill-alert-watcher/alerts/`, not in the worktree, so they never make the tree look dirty; the session is started with `--add-dir` on that folder so it can read them.
  - **The queue is held in memory**, and a restart loses what was waiting. The ledger on disk records only what was acted on, so a lost alert is picked up again by its next hourly repeat.
  - **Node 24's type stripping runs the TypeScript directly**, as `tools/review-marks` does, so there is no build step. `@slack/socket-mode` needs `undici` at run time, as a peer dependency it does not install, so it is a direct dependency here. `just uaw` runs the type check and tests in the frontend dev image, and CI runs the same in the `shell_checks` job, which already sets up Node 24.

## Decisions

- **The watcher stops at a pull request, marked ready for review** - it branches, fixes, tests, pushes and explains in the thread, and a person reviews and merges. A production fault fixed and merged at 3am with nobody looking is exactly the change that most needs a reviewer, and the repository's "never merge" rule already says so. Ready rather than draft, decided on 20 October 2026: a production fix may need merging quickly, and the heavy CI tier runs only once a pull request leaves draft, so a draft would add a step and a wait at the moment neither is wanted.

- **Slack is the trigger, not Cloud Monitoring or GitHub directly** - every alert and every failed workflow already lands in one channel, so watching it covers both sources and puts the watcher's replies next to the alert they answer. Cloud Monitoring's webhook channel and a GitHub webhook were each considered and would have needed an inbound URL on the box, which the Phase 2 rule forbids. Socket Mode was chosen over polling the channel on 20 October 2026: both are outbound only, but polling needs an interval and a last-seen marker and still adds up to that interval of delay, where Socket Mode delivers in a second, makes no calls while idle, and leaves reconnection to Slack's library. Its one cost is a second, app-level token in the env file. Claude in Slack (Claude Tag) was considered too, since an `@Claude` in the alert text starts a cloud session that reports back in the thread, but it needs a Team or Enterprise plan, runs in a cloud sandbox rather than on the box, and the box is the point.

- **The daemon types into an interactive session, not a headless `claude -p`** - a headless run would be tidier to script, with a JSON result and an exit code, but there is nothing to attach to while it runs, and the point of the box is that Mark can pick up any session from the phone or over SSH. Driving the ordinary tmux session with `tmux send-keys` makes worktree 5 the same as worktrees 1 to 4 with one extra typist, at the cost of hooks for busy-tracking and the skill posting its own results to Slack.

- **The watcher's secrets live in the user's home, not in `/etc`** - the first version put the Slack tokens in `/etc/quill-watcher.env`, owned by root at mode 0600, and the log key beside them. A systemd *user* service reads its `EnvironmentFile` as that user, not as root, so it could not have opened either file, and neither could `scripts/slack-reply.sh` running in the session. Moved on 26 October 2026 to `~/.config/quill-alert-watcher/`, mode 0600 and owned by the watcher's user, which is the one account that needs them. Root owning them bought nothing: anything running as that user can already drive the session that holds the tokens in its environment.

- **Read-only log access through a service account, not Mark's login** - a `roles/logging.viewer` key on the box lets the watcher read why an alert fired and nothing else. It is the one runtime credential the box holds, it is read-only, and it is on a machine Mark owns rather than in GitHub, so the rule that CI holds no runtime credentials is kept.
